> **Production-grade digital operations platform for hotels.** Arabic-first RTL UI,
> full booking flow, room management, service requests, communication center,
> audit trail, payments, dashboard analytics — built end-to-end with no
> shortcuts and no white lies.

## Overview

| Layer | Technology | Role |
|---|---|---|
| **Mobile / Web Frontend** | Flutter 3.27 (Dart 3.x) | 23 screens, ~9,000 lines, RTL Arabic, full guest + admin surfaces |
| **Backend API + Auth** | Supabase (Postgres + PostgREST + Auth + Edge Functions) | Single source of truth — RLS-enforced, transactional |
| **Web Host / Edge** | Next.js 16 (standalone build) | Serves the Flutter web bundle + thin orchestration routes |
| **Database** | Supabase Postgres | Prisma schema (581 lines, 22 models) mirrored to Supabase |

The mobile app (iOS / Android) is distributed natively. The web experience is a
**completely separate UI** (also Flutter) — not a stretched-out phone layout.

## Quick start (development)

```bash
# 1. Install deps
bun install

# 2. Configure environment
cp .env.example .env
#   → fill in Supabase URL, anon key, service-role key, DATABASE_URL

# 3. Push Prisma schema to Supabase
bun run db:push

# 4. Build Flutter web (regenerates public/flutter-static/)
bun run build:flutter
#   → requires Flutter SDK on PATH

# 5. Start dev server
bun run dev
#   → http://localhost:3000 (preview only — not a real internet host)
```

## Build & release

See **[BUILD.md](BUILD.md)** for the complete production build guide.

The TL;DR for releases:

```bash
# Tag a release — this triggers the full release pipeline
git tag v1.0.0
git push origin v1.0.0
```

The **Release** workflow will then build and attach:
- `cairo-heart-hotel-web-v{VERSION}.zip` — Flutter Web bundle
- `cairo-heart-hotel-arm64-v8a-v{VERSION}.apk` — Android (arm64)
- `cairo-heart-hotel-armeabi-v7a-v{VERSION}.apk` — Android (armv7)
- `cairo-heart-hotel-x86_64-v{VERSION}.apk` — Android (x86_64)
- `cairo-heart-hotel-universal-v{VERSION}.apk` — Android (fat APK)
- `cairo-heart-hotel-ios-v{VERSION}.ipa` — iOS (unsigned; re-sign before distribution)
- `cairo-heart-hotel-backend-v{VERSION}.tar.gz` — Next.js standalone server

## Production configuration (GitHub Secrets)

Set these in **Settings → Secrets and variables → Actions** before triggering a release:

| Secret | Purpose | Required? |
|---|---|---|
| `PRODUCTION_API_BASE` | The base URL the Flutter app calls (e.g. `https://api.cairoheart.ye`) | Recommended |
| `ANDROID_KEYSTORE_BASE64` | Base64-encoded release keystore (`.jks`) | For Play Store |
| `ANDROID_STORE_PASSWORD` | Keystore password | For Play Store |
| `ANDROID_KEY_PASSWORD` | Key password | For Play Store |
| `ANDROID_KEY_ALIAS` | Key alias | For Play Store |

If signing keys are not configured, the workflow still produces a release-mode
APK signed with the debug key — install it on real devices, but re-sign with a
release key before publishing to Google Play.

## Stack & decisions

- **AD1** — Flutter for **both** mobile and web (single codebase, two UIs).
- **AD2** — Supabase as the **only** backend (PostgREST + Edge Functions + Auth).
- **AD3** — Prisma schema mirrors Supabase tables for type-safe server code.
- **AD4** — RTL Arabic is the first-class language; English is a fallback.
- **AD5** — No blue/indigo palette — gold + dark slate brand.
